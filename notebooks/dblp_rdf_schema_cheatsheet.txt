DBLP RDF Schema Namespaces Cheat Sheet
xsd (http://www.w3.org/2001/XMLSchema#)
Description:  XML Schema Definition datatypes used to type literal values in RDF.
Key datatypes: xsd:string  (string literals), xsd:integer  (integer numbers), xsd:date  and
xsd:gYear  (dates/years), xsd:dateTime  (timestamps), xsd:anyURI  (URI strings), etc. These
provide standard data types for values like titles (strings), publication years (gYear), timestamps,
identifiers (URIs), etc.
rdf (http://www.w3.org/1999/02/22-rdf-syntax-ns#)
Description:  Core RDF syntax namespace defining the basic structure of RDF data.
Key terms: rdf:type  (indicates an instance’s class, used extensively to declare e.g. a resource is a
dblp:Publication  or foaf:Person ), rdf:Property  (class of properties/predicates),
rdf:List , rdf:first /rdf:rest  and rdf:nil  (for RDF lists – though DBLP avoided rdf:List
for creator ordering in favor of a Signature approach ). Also includes rdf:XMLLiteral ,
rdf:langString  for typed literal support.
rdfs (http://www.w3.org/2000/01/rdf-schema#)
Description:  RDF Schema vocabulary for basic ontological relationships and metadata.
Key classes: rdfs:Class  (class of all classes), rdfs:Resource  (everything in RDF graph),
rdfs:Literal  (class of literal values).
Key properties: rdfs:label  (human-readable name of a resource), rdfs:comment
(documentation comment), rdfs:subClassOf  and rdfs:subPropertyOf  (taxonomy relations),
rdfs:domain  and rdfs:range  (typing of properties). DBLP uses RDFS for schema definitions
(e.g., setting domains/ranges for dblp properties and providing labels in the ontology doc).
owl (http://www.w3.org/2002/07/owl#)
Description:  Web Ontology Language namespace, providing advanced ontology constructs beyond
RDFS.
Key terms: owl:Class , owl:ObjectProperty , owl:DatatypeProperty  (types of classes/
properties in OWL). DBLP uses OWL primarily for mappings:
owl:equivalentClass  / owl:equivalentProperty  to state that a dblp class or property is
semantically equivalent to an external one (e.g., dblp:Article  owl:equivalentClass
dbo:AcademicArticle  and schema:Article , or dblp:authoredBy  equivalentProperty
schema:author  etc.).
owl:sameAs  (identity link between individual resources) – not heavily used in DBLP (they prefer
dedicated properties like dblp:wikidata  for linking to Wikidata).
owl:Ontology  (used in the schema definition header).•

bf (http://id.loc.gov/ontologies/bibframe/)
Description:  BIBFRAME (Bibliographic Framework) ontology by the Library of Congress, used for
bibliographic description (especially library catalog data) . Core classes are Work , Instance , Item
(reflecting FRBR-like model: Work = conceptual content, Instance = physical embodiment, Item =
exemplar copy).
Key classes: bf:Work  (abstract creative work – DBLP’s Publication  is aligned here ),
bf:Instance  (a particular edition/instance of a Work, less directly used in DBLP context),
bf:Item  (a single physical or electronic copy of an Instance). Also bf:Agent  (entity such as a
person or organization; DBLP Creator  aligns with Agent , and DBLP specifically subclasses that
into Person, Group, etc).
Key properties:  BIBFRAME properties describe relationships and attributes of resources (e.g.,
bf:contribution  linking an Agent to a Work as an author/editor , bf:identifiedBy  for
identifiers). In the DBLP RDF, BIBFRAME is mainly present to provide class alignments (e.g., Person as
a kind of bf:Agent, Publication as bf:Work) rather than to reuse BIBFRAME properties directly in data.
bibo (http://purl.org/ontology/bibo/)
Description:  Bibliographic Ontology (BIBO) for describing academic publications, documents, and
citations in RDF . It serves as a general vocabulary for scholarly publishing data and can act as a
citation ontology or document classification ontology .
Key classes: bibo:Document  (generic document or publication),
bibo:BibliographicResource  (abstract bibliographic entity – DBLP Publication  is aligned
as a subclass of this ), and more specific types like bibo:Article  / bibo:AcademicArticle
(scholarly journal article – aligns with dblp:Article ), bibo:Book  (dblp:Book  aligns here
), bibo:Thesis  (for theses, which in DBLP may be included under Book),
bibo:ReferenceSource  (encyclopedia or reference entry – aligns with dblp:Reference ),
etc.
Key properties:  BIBO defines many properties for identification and citation:
Identifier properties like bibo:doi , bibo:isbn , bibo:issn . (DBLP uses its own dblp:doi ,
dblp:isbn , etc., but marks them equivalent to these BIBO/other identifier properties .)
Bibliographic detail properties: bibo:pages  (page numbers, used in DBLP as dblp:pagination
equivalent ), bibo:issue , bibo:volume  (for journal issue/volume, though DBLP currently
encodes venue info as strings).
Citation relations: bibo:cites  and bibo:citedBy  (one document cites another). Note:  In the
DBLP dataset, citation links are represented using CiTO’s cito:cites  rather than BIBO’s
properties, but the concept is similar .
Usage in DBLP:  Primarily to align common concepts (Document, Article, etc.) and identifier usage.
For example, DBLP equates its Article class to BIBO’s AcademicArticle  and uses BIBO’s notion of
Document as a super-class of publications .

provides classes and properties mirroring BibTeX entry types and fields, facilitating integration of
BibTeX data on the Semantic Web.•

Key classes:  The ontology’s base class is bibtex:Entry  (a bibliographic entry). Under it are
classes corresponding to BibTeX entry types (nearly all classes come directly from the BibTeX format
):
bibtex:Article  (an article in a journal or magazine),
bibtex:InProceedings  (a conference paper in proceedings),
bibtex:Book , bibtex:InCollection  (book chapters), bibtex:Proceedings ,
bibtex:PhDThesis , bibtex:Mastersthesis , etc., matching the standard BibTeX types.
Key properties:  Similarly, properties correspond to BibTeX fields:
e.g., bibtex:hasAuthor , bibtex:hasEditor  (authors/editors list), bibtex:hasTitle ,
bibtex:hasYear , bibtex:hasJournal  (journal name for articles), bibtex:hasPublisher ,
bibtex:hasPages , etc.
These properties often expect literal values (strings, numbers) as in a .bib file.
Usage in DBLP:  DBLP’s own ontology defines its publication types and properties, but it includes the
BibTeX ontology mainly for interoperability. Each dblp:Publication  has a dblp:bibtexType
property whose value is a BibTeX class indicating the traditional type (e.g., an inproceedings paper
will have dblp:bibtexType bibtex:InProceedings ). This helps in generating BibTeX or
aligning with systems that use BibTeX classes. The actual metadata fields in DBLP (title, authors,
year) are given by DBLP properties (e.g., dblp:title , dblp:yearOfPublication ) rather than
using bibtex:hasTitle  directly.
cito (http://purl.org/spar/cito/)
Description:  CiTO, the Citation Typing Ontology, is an ontology for modeling citation links and their
nature in scholarly data . It enables characterization of the type of citation (supporting, disputing,
etc.), but also provides a simple way to represent that one work cites another .
Key classes:  CiTO’s focus is on relationships, not new document classes. (It does define a class like
cito:CitationAct for a citation event, but in basic usage one doesn’t usually instantiate this for each
citation unless modeling citation contexts.)
Key properties:  The core object properties are:
cito:cites  – indicating that one bibliographic entity cites another . In the DBLP RDF data,
each known reference from one publication to another is represented with this property (e.g.,
<PaperA> cito:cites <PaperB>  means PaperA’s reference list includes PaperB). This is
especially used now that DBLP has integrated citation data from OpenCitations.
cito:isCitedBy  – the inverse property (not always explicitly stored, but inferred as the inverse of
cito:cites).
CiTO includes many sub-properties of cito:cites to categorize the nature of a citation (e.g.,
cito:extends, cito:usesMethodIn, etc.), but these specific types are not explicitly used in DBLP; DBLP
uses cito in a basic way to denote citation links.
Usage in DBLP:  Provides a standard way to represent citation relationships between publications in
the graph (each citation is a triple using cito:cites ). This makes it easier to query for papers that
cite or are cited by others.

classes and properties that complement the DataCite metadata schema (which is used for datasets
and research outputs).
Key classes:
datacite:Identifier  – a class for identifiable things (used when assigning external identifiers
to entities).
datacite:IdentifierScheme  – an enumeration class for types of identifier schemes . Specific
instances of this class (named individuals) represent schemes like DOI, ISBN, ORCID, etc.
(It also defines classes for parts of metadata, like datacite:Resource, datacite:Agent, but in DBLP
context the focus is on identifiers.)
Key named individuals (Identifier Schemes):  DataCite ontology provides built-in individuals for
many identifier types . For example, datacite:doi  (the DOI scheme), datacite:issn ,
datacite:isbn , datacite:orcid , datacite:ark , etc., are defined as instances of
datacite:IdentifierScheme. DBLP leverages these: e.g., the property dblp:doi  is declared
equivalent to the DOI identifier in both the LoC and DataCite vocabularies . Similarly,
dblp:orcid  (for author ORCIDs) is aligned with datacite:orcid .
Key properties:
datacite:hasIdentifier  – relates an entity to a datacite:Identifier (which might carry a literal or
further info).
datacite:usesIdentifierScheme  – links an Identifier to a datacite:IdentifierScheme (e.g., a
specific DOI string is used with the DOI scheme).
In practice, DBLP doesn’t model each identifier as a full node with datacite classes; instead it
provides identifier values as literals (or as URIs for ORCID/DOI) and simply uses the known scheme
individuals for equivalences. So you won’t commonly see datacite:hasIdentifier  in the triples;
instead you’ll see, for example, <paper> dblp:doi "10.xxxx/..."^^xsd:anyURI , and know
via schema that dblp:doi is an identifier of type DOI .
Usage in DBLP:  Primarily to formally denote identifier types. The DBLP ontology marks dblp:doi
as equivalent to datacite:doi , dblp:isbn  equivalent to datacite:isbn , etc., using
DataCite’s identifier scheme individuals. This helps in interoperability (so external tools know, for
example, that dblp:doi  is a DOI). It’s also used for the concept of Open Metadata ID
(dblp:omid ) which likely aligns with an identifier in DataCite’s list (OMID appears as a DataCite
individual in their list of schemes ).
dbo (http://dbpedia.org/ontology/)
Description:  DBpedia Ontology – a broad, cross-domain ontology derived from Wikipedia infoboxes.
It defines classes and properties for common concepts (people, places, creative works, etc.) used in
the DBpedia knowledge base.
Key classes:
dbo:Person  (the class of people – DBLP’s dblp:Person  is aligned with this),
dbo:Agent  (general class of agents; similar to FOAF Agent or schema Person/Org, also used as a
super-class for creators ),
dbo:WrittenWork  or dbo:Work  (class for written creative works – DBLP Publication  is
linked to dbo:WrittenWork ),
dbo:AcademicArticle  / dbo:Article  (DBpedia has classes for specific types of works; e.g.,
dbo:AcademicArticle  could correspond to scholarly articles, and dblp:Article  is mapped to
dbo:Article ).

Properties in DBpedia ontology often mirror natural-language infobox properties. Relevant ones
include dbo:author  (links a Work to a Person author), dbo:editor  (links a Work to an editor),
dbo:publisher , dbo:publicationDate  (for publication date).
In DBLP’s schema alignment, for instance, dblp:authoredBy  (publication to creator) is stated as
equivalent to dbo:author , and dblp:editedBy  equivalent to dbo:editor . Also,
dblp:yearOfPublication  (year) is equated to dbo:publicationDate  (though DBpedia’s
property expects a full date) .
Usage in DBLP:  The DBpedia ontology is used to align DBLP classes/properties with a well-known
general ontology. This means external semantic web users can infer , e.g., a dblp:Publication  is
a kind of dbo:WrittenWork , and use generic properties. For example, queries could use
dbo:author  or schema:author  interchangeably with dblp:authoredBy  thanks to the
equivalences.
dc (http://purl.org/dc/elements/1.1/)
Description:  Dublin Core Metadata Element Set, Version 1.1 – a set of 15 basic metadata properties
for broad use in resource description (created by DCMI). It includes generic terms like Title, Creator ,
Date, etc., meant to be simple and cross-domain .
Key properties (elements):  Classic Dublin Core elements include:
dc:title  (the title of the resource),
dc:creator  (the creator/author of the resource),
dc:subject  (topic keywords),
dc:date  (a date associated with the resource, often publication date),
dc:type , dc:format , dc:identifier , etc.
Usage in DBLP:  The DBLP RDF schema maps some of its properties to Dublin Core for
interoperability. For example, dblp:title  is a publication title and is aligned with dc:title
. Similarly, an author in DBLP could be aligned with dc:creator  (or more precisely
dcterms:creator; see below). The DBLP dataset itself primarily uses its own properties, but
acknowledging the DC equivalents makes it easier for generic metadata processing. Dublin Core
elements are broad and sometimes superseded by the more precise DC Terms (dct). In summary, DC
offers a baseline: e.g., one can treat dblp:title  as a kind of dc:title  in a pinch, since it
represents the title of a bibliographic resource.
dct (http://purl.org/dc/terms/)
Description:  Dublin Core Metadata Terms  – an updated and expanded set of metadata terms that
refines the original DC elements. It includes qualifiers and additional classes, and is designed to be
used in modern RDF contexts (range domains, etc.).
Key classes:
dct:Agent  (a class for agents, i.e., people or organizations involved in the lifecycle of a resource –
DBLP creators align with this as one of their super-classes ),
dct:BibliographicResource  (class for a document or publication – DBLP Publication  aligns
with this concept ).
Key properties:
dct:creator  (equivalent to the dc:creator element but in the refined schema; domain includes
dct:Agent, range a resource – DBLP maps dblp:createdBy/authorOf  to this ),•

foaf (http://xmlns.com/foaf/0.1/)
Description:  FOAF (Friend of a Friend) is a well-known ontology for describing people, their
relationships, and related things (like organizations, documents) in RDF . It’s often used for
linking person identities and basic personal info.
Key classes:
foaf:Person  (class of people – DBLP Person is mapped to foaf:Person),
foaf:Organization  (for institutions, though DBLP doesn’t yet model affiliations as separate org
entities in the RDF, this could be relevant in future),
foaf:Agent  (superclass of Person and Organization – DBLP Creator  counts as a foaf:Agent
),
foaf:Document  (class of documents or web pages – used in DBLP for things like an external
webpage link’s range , e.g., dblp:webpage has range foaf:Document).
Key properties:
foaf:name  (a person's name – DBLP uses its own dblp:creatorName  but marks foaf:name as a
super-property/equivalent , meaning the full name of a creator can be seen as a foaf:name ),
foaf:homepage  (URL of a personal homepage – dblp:homepage  for a creator is equivalent to
foaf:homepage ),
foaf:page  (a generic page about something – DBLP’s dblp:webpage  (for any entity’s related
page) is aligned with foaf:page ),
foaf:knows  (represents a person knowing another – DBLP uses this concept indirectly:
dblp:coAuthorWith  and other co-creator relationships are sub-properties of a generalized co-
creator relation which is aligned to foaf:knows . Essentially, if two authors have co-authored,
DBLP signals that as a kind of “knows” relationship in FOAF terms).
foaf:maker  (links a foaf:Document to the foaf:Agent that made it) – DBLP aligns
dblp:createdBy  (publication to creator) with foaf:maker , meaning a publication’s creator can
be viewed via the foaf:maker predicate.
Usage in DBLP:  FOAF is used to ensure person entities and their properties are recognized by a
common schema. For example, an external application could see a DBLP author node and because
it’s typed as foaf:Person and has a foaf:name, it knows how to treat it. Also, links like homepage or
Wikipedia pages for authors are easily understood via FOAF terms.•

litre (http://purl.org/spar/literal/)
Description:  The SPAR Literal Reification  ontology (prefix litre) provides a pattern for treating
literals (strings, numbers) as first-class entities when needed . Normally in RDF, literal values
cannot be subjects of triples; this ontology creates a way to “reify” a literal into a resource, so you can
attach additional information to it.
Key class: litre:Literal  (sometimes referred to as a reified literal or literal entity ). An
instance of this class represents a specific literal value as an individual node.
Key properties:
litre:hasLiteralValue  – a data property  linking a litre:Literal  individual to the actual
literal (string or other datatype) it represents . Each litre:Literal  must have exactly one
such value (the actual content of the literal) .
litre:hasLiteral  – an object property  that links a resource to a litre:Literal  (i.e. to a
reified literal node) . Inverse is litre:isLiteralOf .
litre:hasSameLiteralValueAs  – an object property to relate two literal-reified individuals that
carry the same string/value (useful for equality comparison) .
Usage in DBLP:  This ontology is included for potential cases where DBLP might need to model a
literal with extra metadata. For example, if an author’s name (a literal string) needed to be an object
of triples (to annotate it or link it to another concept), one could create a litre:Literal  node for
the name. As of the current schema, DBLP doesn’t heavily use literal reification (most data are either
simple literals or full resources), but having the namespace signals that it’s available. It might be
used behind the scenes or for future extensions (e.g., managing alternate names or titles as
resources). In summary, litre provides a technical solution for edge cases involving literals as
subjects.
locid (http://id.loc.gov/vocabulary/identifiers/)
Description:  Library of Congress Identifiers vocabulary – a controlled list of identifier types
maintained by LoC. Each term in this vocabulary represents a well-known identifier scheme (similar
purpose to DataCite’s list of schemes).
Key terms:  These are typically modeled as individual entries (not classes or properties, but instances
in the LoC identifiers scheme). Relevant ones in DBLP context include:
locid:doi  (the DOI identifier scheme, i.e., an entry representing “Digital Object Identifier”),
locid:isbn  (International Standard Book Number scheme),
locid:issn  (International Standard Serial Number),
locid:orcid  (Open Researcher and Contributor ID for author IDs),
locid:ark , locid:handle , etc., and many others (the LoC list is extensive).
Usage in DBLP:  Similar to DataCite, DBLP uses these as reference points for its identifier properties.
For example, dblp:doi  is stated to be equivalent to locid:doi , dblp:isbn  to locid:isbn ,
dblp:issn  to locid:issn , and dblp:orcid  to locid:orcid . This means when you see a DOI
in the DBLP RDF, it’s not only a string or URI, but the property carrying it is linked to the formal
concept of a DOI as defined by the Library of Congress. Essentially, DBLP declares “our DOI property
is the same as the concept of DOI in the LoC identifiers vocabulary.” This helps in linking with library
data or any system that also uses the LoC’s vocabulary for identifiers. (There are no unique classes or
properties introduced from locid into the DBLP data; it’s purely for equivalence mapping of identifier
semantics.)•

locrel (http://id.loc.gov/vocabulary/relators/)
Description:  Library of Congress Relators – a vocabulary of roles that a person or organization can
play with respect to a bibliographic item. These are the standard MARC Relator codes (typically 3-
letter codes) with URIs. Each code has a meaning (e.g., aut = author , edt = editor , ill = illustrator , etc.).
Key terms:  Each relator code is represented as an RDF resource (many are skos:Concepts in LoC’s
data, but they can be used to tag relationships). Notable codes in the DBLP context:
locrel:aut  – Author  role ,
locrel:edt  – Editor  role ,
locrel:cre  – Creator  (a generic creator role, often encompassing author or editor) .
(Dozens of others exist, like trl for translator , but DBLP currently concerns mainly authors/editors
of works.)
Usage in DBLP:  The DBLP ontology maps its creator relationships to these relator terms for clarity.
For example, dblp:authoredBy  (linking a publication to a creator in the author role) is said to be
equivalent to locrel:aut , and dblp:editedBy  equivalent to locrel:edt .
dblp:createdBy  (a super-property for “has creator”) is aligned with a general creator code
locrel:cre . This means DBLP is leveraging library standards to denote the role of the person
in relation to the publication. In SPARQL, one could use these relator URIs similarly to the dblp
properties (but typically one uses the dblp properties directly; the mapping just makes the semantics
clear). Essentially, the LoC relator namespace provides a shared understanding that, say, an “author”
relationship in DBLP is the same as an “author [aut]” in library terms.
schema (https://schema.org/)
Description:  Schema.org vocabulary – a broad collection of schema definitions for entities and
relationships used in web markup (created by major search engines). It includes types for creative
works and scholarly articles, making it relevant for bibliographic data.
Key classes:
schema:CreativeWork  (a generic creative work, parent class for many things – DBLP’s
publications correspond to CreativeWork , and DBLP Stream (venue) is aligned as a
CreativeWorkSeries ),
schema:Article  (an article, typically in a magazine or journal – dblp:Article  is linked to
schema:Article ; schema also has ScholarlyArticle  subclass but DBLP used the more
general Article class),
schema:Book  (dblp:Book  aligns with schema:Book ),
schema:Dataset  (dblp:Data  is aligned with schema:Dataset , reflecting datasets as first-
class entities in DBLP),
schema:Person  (dblp:Person  maps to schema:Person  via foaf and others, since
schema:Person is akin to foaf:Person),
schema:Organization  (not directly used yet, but likely relevant when institutions are added as
entities in DBLP).
schema:CreativeWorkSeries  (a series of publications – dblp:Stream  which represents a
conference series or journal is mapped to this ).

wd (http://www.wikidata.org/entity/)
Description:  Wikidata entity namespace. Wikidata is a crowd-sourced knowledge base; each entity
(item) has a unique ID (Q-number). The wd: prefix is used for those item URIs.
Usage in DBLP:  DBLP uses Wikidata links to connect its entities to corresponding Wikidata entries.
For example, many authors in DBLP are linked via a property dblp:wikidata  to a wd:Q...
identifier . Likewise, some venue series or conferences might be linked to Wikidata items.
The DBLP ontology defines dblp:wikidata  as a property for this and marks it as an
identifier  sub-property . This is essentially a same-as link without using owl:sameAs
explicitly.
Additionally, in the ontology reference, DBLP classes have equivalences to Wikidata classes (items).
For instance, dblp:Person  is equivalent to Wikidata item Q5 (which is the item for “human”) .
dblp:Conference  series is equated to a Wikidata item for conference series (e.g., Q47258130)
, dblp:Journal  to Q5633421 perhaps, etc. These alignments tie DBLP’s notion of entities to
Wikidata’s ontology via specific Q-IDs.
Key points:  Since wd: items are just identifiers (not classes or properties themselves in the schema
sense), “key classes” would refer to notable Q-items used for mapping:
Q5 (human) for Person,
Q571 (book) for Book ,
Q13442814 (scholarly article) for Article ,
Q17051824 (dataset) for Data ,
etc. These show up in the ontology as equivalents to dblp classes. For querying, one might use them
if doing federated queries with Wikidata or to fetch additional info about an entity from Wikidata.
Practical SPARQL tip:  If you have a DBLP resource with a known Wikidata link, you could include the
wd: namespace to bring Wikidata data (via federated query or if imported). For example, find an
author’s country by using the DBLP–Wikidata link to join to Wikidata’s data. The presence of wd: in
the prefix list tells us such linking is available.•

wdt (http://www.wikidata.org/prop/direct/)
Description:  Wikidata direct property  namespace. In Wikidata, properties are identified as P-
numbers (e.g., P50 for “author” of a work, P577 for “publication date”). The wdt: prefix allows
direct use of these properties to get values (bypassing qualifiers/rank, etc.).
Key properties:  Relevant ones to scholarly data include:
wdt:P50  – “author” in Wikidata (links a work item to a person item). DBLP maps
dblp:authoredBy  to wdt:P50 in its ontology equivalences .
wdt:P98  – “editor” (Wikidata property for editor of a written work). Mapped from
dblp:editedBy .
wdt:P31  – the ubiquitous “instance of” property. (Not directly mapped in DBLP, but DBLP classes
themselves correspond to certain Q-items as instance-of relationships in Wikidata.)
wdt:P1476  – “title” of a creative work (DBLP title is aligned with this ).
wdt:P356  – DOI of a publication (DBLP doi might align conceptually with this, though DBLP uses
its own property for DOI).
wdt:P577  – publication date (mapped to dblp:yearOfPublication  in equivalence ).
wdt:P17  (country, for affiliation country if needed) and others, which might be used indirectly if
one connects authors to their country via Wikidata.
Usage in DBLP context:  DBLP itself doesn’t include wdt:P… predicates in its data; however , by
listing this prefix, it signals that queries could utilize Wikidata properties when federating or when
referring to mapped properties:
For example, since dblp:yearOfPublication  ≡ wdt:P577 , one could use wdt:P577  in a
query if combining DBLP data with Wikidata to fetch the publication date (year).
Or one might use wdt:P50  to get all authors of a work via Wikidata, but in the DBLP graph it’s
easier to just use dblp:authoredBy . The mapping just confirms they mean the same relation of
“authorship”.
Federation scenario:  If you had both DBLP and Wikidata accessible in a SPARQL environment, you
could do something like: select a DBLP paper , find its Wikidata ID via dblp:wikidata , then join to
Wikidata’s endpoint to get extra info (like ?paper wdt:P50 ?author_wd  to get the author item
from Wikidata, which might have more data such as birth year , etc.). The inclusion of wdt: makes
such cross-queries feasible.

dblp:Creator  – superclass for any entity that creates publications . Subclasses:
dblp:Person  (an individual human researcher) ,
dblp:Group  (a group or consortium of people acting as an author – used rarely, e.g.,

dblp:AmbiguousCreator  (special class for an author identity that is known to be
ambiguous, i.e., multiple people mixed under one name until disambiguated  – used

dblp:Signature  – a reification class representing the authorship/editorship link between a
publication and a creator . Each Signature is like an authorship instance:
Subclasses: dblp:AuthorSignature  (an authorship record) and
dblp:EditorSignature  (an editorship record) .
Each dblp:Signature links exactly one publication and one creator , and carries metadata like
author order and possibly an ORCID for that specific authorship .
dblp:Stream  – represents a “publication stream”, i.e., a venue or series (added in the 2024 extension)

Subclasses: dblp:Conference  (conference series), dblp:Journal  (journal as a whole),
dblp:Series  (book series or numbered conference proceedings series),
dblp:Repository  (for data repositories/collections like Zenodo, etc.) .
Streams are the entities to which publications are linked to indicate where they appeared. For
example, a paper in ICML 2023 would have a stream of dblp:Conference “ICML” and possibly
also a dblp:Series if that conference’s proceedings belong to a series.
dblp:Entity  – a general super-class for all “named” entities in the DBLP KG (covers Creator ,
Publication, Stream) . Used as a domain for generic properties like homepage, identifiers, etc.
dblp:VersionRelation  – a class representing a relationship between two versions of a publication
(e.g., a preprint vs. its journal version) . It links a general publication concept and a specific
version.

Summary usage:  The DBLP namespace is the core of any SPARQL on the DBLP data. Typical queries
will:
Select things by rdf:type  (e.g., ?pub rdf:type dblp:Publication  to get publications, or a
specific subclass like dblp:Article).
Traverse relations like dblp:authoredBy  to get authors, or use the Signature pattern ( ?pub
dblp:hasSignature ?sig . ?sig dblp:signatureCreator ?person . ?sig
dblp:signatureOrdinal ?order  to get ordered authors).
Filter by attributes like title or year ( ?pub dblp:title ?t; dblp:yearOfPublication ?y ).
Use dblp:publishedInStream  to find venue information, then maybe get ?pub
dblp:publishedInStream ?venue . ?venue rdf:type dblp:Journal  etc.
Use the equivalences if needed – e.g., you could query for ?pub schema:author ?pers  instead
of dblp:authoredBy ?pers  because of the equivalence, but using the dblp terms directly is
straightforward.
Leverage the identifier links: find a publication by DOI ( ?pub dblp:doi
"10.1145/1234..."^^xsd:anyURI ) or find a person by ORCID ( ?person dblp:orcid
<https://orcid.org/....> ).
Explore coauthor networks via dblp:coAuthorWith  (this is a symmetric relation on Person: ?
person dblp:coAuthorWith ?colleague  finds co-authors).
Connect to external data: go from a DBLP entity to Wikidata
(?person dblp:wikidata wd:QXXXX ) to fetch more info from Wikidata if needed.
Each of the above namespaces contributes to the rich semantics of the DBLP data. Together , they make the
DBLP RDF a well-integrated part of the Linked Open Data cloud, enabling advanced queries and data
integration across bibliographic databases .•
